# 原型制作规范

- 状态：Draft（待评审后转 Accepted）
- 适用范围：`docs/prototypes/` 下所有原型与说明
- 建立日期：2026-09-15
- 文档版本：v0.6

## 1. 原则

1. **保真度按用途分级**，见 §2。完整页面清单用 **F3 结构稿**，单点争议用 **F1 线框**。任何级别都不做像素级视觉定稿；有争议处用文字标注，而不是用像素推敲替代产品讨论。
2. **自包含单文件**：每个原型是一个 `index.html`，样式内联，无外部依赖、无构建、无网络请求。保证任何机器、任何时间双击即可打开。
3. **一图一说明**：同目录必须有 `README.md`，且与 HTML 内容一致。二者冲突时以 README 为准，并立即修 HTML。
4. **标注实现映射**：说明必须写明「设计对应哪些代码路径」和「哪些部分尚未实现」，避免原型被当成完成证据。
5. **不改契约**：原型不得引入新的协议字段、密码学参数、状态机状态、API 路径或数据库表。需要新概念时，先改 `docs/architecture/`、`docs/product/` 或新写 ADR。
6. **原型不是证据**：任何「已实现 / 已验证」结论只能来自代码、提交、CI 与验证报告，引用规则见 `docs/README.md` §5。

## 2. 保真度分级

| 级别 | 名称 | 用途 | 必须包含 | 不要求 |
| --- | --- | --- | --- | --- |
| **F1** | 线框 | 讨论单个结构或流程争议 | 框线、层级关系、关键文案 | 真实字段、完整导航、状态变体 |
| **F2** | 局部稿 | 单个页面或单个组件的设计确认 | 完整页面结构、真实字段名 | 全站导航一致性、多状态矩阵 |
| **F3** | 结构稿 | **完整页面清单交付**（默认级别） | 应用外壳（导航/顶栏）、页面头、真实字段与示例值、操作按钮、状态变体、空/错/无权限态 | 配色定稿、图标定稿、动效、间距像素级还原 |
| **F4** | 还原稿 | **照现有实现复刻**，用于对照、验收与回归 | F3 全部 + 样式与结构取自真实源码/构建产物 | 可运行交互（静态展示即可） |

规则：

- **交付完整页面清单时必须用 F3。** 只有 F1/F2 的清单不能称为"完整页面图"。
- **F4 只在有真实实现可读时使用。** 无源码可依据时不得标 F4，否则与 F1/F2 无从区分，等同于虚构。
- F4 必须在 README 中逐项列出**还原来源**（文件路径）与**还原偏差**（哪些是自己加的、哪些取不到）。
- **F4 的样式来源优先级**：① 项目自有 CSS 原文 ② 依赖包源码/构建产物 ③ 无包可读时按组件库设计变量重建 —— **用 ③ 时必须在文件头与 README 同时标注「外壳为重建，非逐像素」**，不得笼统声称"一模一样"。子代理容易在此处过度承诺。
- **"本地没装依赖"不等于"读不到依赖包"**：可以只把目标包下载到**仓库之外的临时目录**解析，不在项目里产生 `node_modules`：
  ```bash
  mkdir -p /tmp/proto-ref/<pkg> && cd /tmp/proto-ref/<pkg>
  curl -sSL -o pkg.tgz https://registry.npmjs.org/<name>/-/<name>-<version>.tgz
  tar xzf pkg.tgz
  ```
  许多包会在 tarball 里附带 `src/` 源码、默认配置与 i18n 文案，足以取到主题 token、布局参数、菜单名与组件实现。**走这条路径时必须在 README 记录包名、版本、integrity 与解析出的关键实数**，让结论可复核。**不允许把包内容或依赖树装进仓库。**
- F3 不得退化为"只有标题的占位块"：每个页面必须有可读的真实字段、状态徽标与操作入口。
- 升级保真度不改变 §5 的版本规则；F1 → F3 属于 MINOR（同结构下表达完善），页面集合变化才属于 MAJOR。
- F3 的「状态变体」要求：列表页至少给出正常、空、错误、无权限；会话类页面至少给出连接态与执行态的组合。
- 自包含单文件约束在 F4 下依然生效：**不得**为了还原而引入外部 CSS/字体/脚本；把需要的样式文本内联进来。

## 3. 必须标注的字段

`README.md` 头部字段：

```text
- 版本：vX.Y
- 状态：Design only | Partial impl | Visual baseline | Superseded
- 保真度：F1 | F2 | F3 | F4
- 界面：一句话
- 使用者：最终用户 | 管理员 | 运维
- 关联文档：相对路径
- 关联代码：仓库相对路径，或「无」
- 已实现部分：
- 未实现部分：
- 非目标：
- 首次建立：YYYY-MM-DD
- 最后更新：YYYY-MM-DD
```

同时，`index.html` 顶部必须显示版本与状态徽标（`.badge--ver` + 状态徽标），让脱离 README 单独打开文件的人也能看到。

**页面清单类原型额外要求**：README 必须有一张页面清单表，含「页面 / 路由或入口 / 实现状态」三列；`index.html` 必须有对应的页面地图与清单表。实现状态取值统一为 `已实现` / `部分实现` / `未实现` / `Foundation`，并声明它不改变 `docs/roadmap/` 与验证报告的结论。

### 状态标签语义

| 标签 | 含义 | 判定依据 |
| --- | --- | --- |
| `Design only` | 仅设计，代码中无对应实现 | 在 `platform/`、`aba/`、`hc/` 中找不到对应代码路径 |
| `Partial impl` | 代码中有部分实现，原型包含未实现部分 | 已在 README「已实现 / 未实现」中逐条列明 |
| `Visual baseline` | 对应界面已实现并验收，原型作为视觉与回归参照 | 有对应验证报告 |
| `Superseded` | 已被新原型取代，保留历史 | README 指向新目录 |

## 4. 命名

- 目录：kebab-case，描述界面而非技术实现。用 `hc-pages/`、`platform-pages/`，不用 `screen-1/` 或 `figma-export-3/`。
- 一个前端面（surface）一个目录：一个端最多的完整页面集合放在同一个目录里，多形态（移动 + 桌面）在同一 `index.html` 内对比。
- 被取代的**大版本**：保留目录并改名为 `<name>-v<MAJOR>/`，README 标 `Superseded` 并指向新目录。不删除历史。

## 5. 版本编号与变更记录

每个原型**独立编号**，格式 `vMAJOR.MINOR`。

### 5.1 版本动作

**Draft 阶段（MAJOR = 0）**：原型尚未定稿，页面集合、导航层级、关键流程、保真度等级的变化**一律 `MINOR + 1`**，不切 `<name>-vN/` 目录、不归档旧版。当前所有原型都在此阶段。

**定稿基线之后（MAJOR ≥ 1）**：

| 变化类型 | 版本动作 |
| --- | --- |
| 信息架构、导航层级、关键流程、页面集合变化 | `MAJOR + 1`，需重新评审；旧版通过 `<name>-v<MAJOR>/` 目录保留并标 `Superseded` |
| 同结构下的布局、文案、状态表达、保真度升级 | `MINOR + 1` |
| 纯错别字、注释修正，不影响设计表达 | 不改版本号，仅在版本记录里注明修订 |

草案定稿并转为基线时版本号为 `v1.0` —— 这是唯一允许出现 `1.0` 的场合。首个版本仍一律 `v0.1`。

### 5.2 强制规则

1. 版本号必须同时出现在**三处并保持一致**：
   - 本目录 `README.md` 头部「版本」字段；
   - `index.html` 顶部 `vX.Y` 徽标，**该元素必须带 `badge--ver` 类**（可与其他样式类共存），便于脚本校验；
   - 总入口 `docs/prototypes/README.md` §3 原型清单表的「版本」列。
   任一处缺失即视为不合格原型。
2. 每次版本变化必须在 README 的「版本记录」表**新增一行**，不得改写历史行：

   ```markdown
   | 版本 | 日期 | 变更 | 触发文档 / 决策 |
   | --- | --- | --- | --- |
   | v0.1 | 2026-09-15 | 首次建立 | `docs/remote/README.md` §9 |
   | v0.2 | 2026-09-16 | 输入区增加取消待确认状态 | <会议或 ADR 引用> |
   ```

3. **版本号只标识设计稿迭代。** 它不是 Platform、ABA、HC 的产品版本，不代表实现进度，也不得被引用为「已发布」「已上线」的依据。禁止使用 `1.0.0`、`v1.0` 这类容易被误读为产品版本的写法，首个版本一律 `v0.1`（定稿基线转为 `v1.0` 的情形见 §5.1）。
4. 原型版本号与 Git 分支名无关：分支只承载提交，版本体现在文件内容与 README 里。
5. 不得静默覆盖已评审版本。被取代的大版本必须能在 `<name>-v<MAJOR>/` 目录或 Git 历史中找到。
6. 原型版本变化若反映产品决策变化，必须在同一检查点把结论写回 `docs/architecture/`、`docs/product/` 或 ADR。

## 6. 主题与可读性

- **浅色优先**，同时用 `@media (prefers-color-scheme: dark)` 提供深色。两套配色都要能看清。
- 文字与背景对比度满足 WCAG AA：正文 ≥ 4.5:1。
- **颜色不能是唯一语义**：风险等级、连接状态、`UNCERTAIN`、实现状态必须同时有文字说明。
- 最小字号 12px；正文 13–14px。不用全大写、不用斜体传达状态。
- 不使用渐变、阴影堆叠、模糊、发光等装饰效果。

## 7. 禁止事项

- 真实或看似真实的密钥、Token、Ticket、证书序列号、指纹。
- 真实生产域名、内网地址、客户名。统一用 `example.invalid`、`198.51.100.0/24`、`203.0.113.0/24`、`aba-lab-01`、`hc-web-lab` 这类保留示例值。**例外**：`127.0.0.1` / `localhost` 加端口可以照用，因为它是本机回环地址、不含环境信息；已验证的本地开发地址（如验收报告记录的 `127.0.0.1:8001`）优先于虚构域名，因为它有据可查。
- 真实用户数据、聊天内容、源码片段或工具参数。
- 外部 CDN、脚本、字体、图片。图标使用内联 SVG 或字符。
- 展示内部堆栈、SQL、真实本地路径、密钥材料（对应 `docs/architecture/HC.md` §23）。
- 用表情符号代替状态标签或版本号。
- 把未实现能力画成已完成，或用「已上线」「生产可用」等措辞描述设计稿。F3 页面稿尤其容易产生这种误读，必须在页面地图、清单表和页脚同时标注实现状态。

## 8. 安全相关 UI 必须表达的部分

以下内容来自已接受的架构与安全契约，原型不得省略或弱化：

| 场景 | 原型必须体现 | 依据 |
| --- | --- | --- |
| Opaque 模式 | 「会话内容在此 HC 与 ABA 之间加密」「Platform 可见连接、时间、大小和路由元数据」 | `HC.md` §21 |
| `UNCERTAIN` | 置顶显示、要求用户选择、明确「不自动重试」 | `HC.md` §19、D-029 |
| 权限卡 | 来源 ABA/Agent、Session/Workspace、工具类型、目标摘要、风险等级、允许范围与有效期；三个按钮，无「永久允许所有命令」 | `HC.md` §16 |
| 背压 | 显示 Backpressure / 重连状态，不静默排队 | `HC.md` §17 |
| 吊销 | 停止连接、清除本地可撤销凭据、不自动重注册 | `HC.md` §11、D-031 |
| 状态展示 | **执行状态与连接状态分开展示** | `docs/remote/README.md` §9 |
| Managed Mode | 若有入口，必须写明「Platform 可以读取内容」，且不使用绿色 E2EE 标识 | `HC.md` §22 |
| 平台侧权限 | 前端隐藏不授权；后端权限为最终权威；403 为正常兜底 | AGENT.md §3.7 |
| 平台侧交付 | ACK 表示安全接收，不等于本地 Agent 已执行；无「重试执行」 | D-028 |

## 9. 评审流程

```text
原型草案（docs/prototypes/）
  -> 与相关 architecture / product / ADR 对照评审
  -> 结论写回正式文档（architecture / product / ADR）
  -> 实现（platform / aba / hc）
  -> 用 docs/roadmap/verification/ 记录真实证据
```

原型讨论产生的结论**不能只留在原型里**。没有写回正式文档的结论，下次会话不予承认。

## 10. 维护

- 原型外观变化若反映产品决策变化，必须在同一检查点更新对应正式文档。
- **实现状态列是义务**：每次实现推进后，同步更新清单表的实现状态；长期未更新的状态列比没有状态列更有害。
- 长期不维护、且对应界面已明显演进的 `Visual baseline` 原型，应改为 `Superseded` 或更新，不要保留误导性版本。
- 版本号只在设计稿内容变化时递增；不要为了「看起来有进展」而刷版本。
